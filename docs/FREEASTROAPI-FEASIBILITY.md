# FreeAstroAPI feasibility and risk assessment for Mantrilo

**Verdict: Proceed with caveats.** FreeAstroAPI v2 is a good candidate for a synthetic pilot covering D1, D9 and daily Panchang. Its published coverage is sufficient for a first integration, but production readiness depends on independent accuracy checks, capacity for launch traffic, and written permission for Mantrilo to serve results to its own API customers. Leave the existing Mantrilo calculation endpoint on its current engine during the evaluation.

This is a review of the vendor's published contract, schemas and examples. No authenticated vendor requests, latency measurements, accuracy comparisons or contractual SLA verification have been completed.

## Feasibility matrix

| Area | Documented support and value to Mantrilo | Gap and production decision |
| --- | --- | --- |
| Sidereal D1 Rasi | V2 returns the ascendant, graha positions, houses, nakshatras and calculation metadata. Lahiri, whole-sign houses and mean or true nodes are configurable. [Basic Vedic chart](https://www.freeastroapi.com/docs/vedic/chart) | Pin these options and verify longitude, ascendant, sign and nakshatra boundary cases. Keep date-dependent Sade Sati out of a permanent birth chart snapshot. |
| D9 Navamsha and vargas | Dedicated divisional calculations and a combined request that can return D1 and D9 together. The combined endpoint lets callers omit unneeded modules. [Vargas](https://www.freeastroapi.com/docs/vedic/vargas) · [Full calculation](https://www.freeastroapi.com/docs/vedic/calculate) | Test each supported division before exposing it. D9 is especially sensitive to ascendant or planetary positions near a division boundary. The basic and combined endpoints have different response shapes. |
| Vimshottari Dasha | V2 provides Mahadasha, Antardasha and Pratyantardasha, including current periods and timelines. The combined endpoint accepts a reference date and depth. [Vimshottari Dasha](https://www.freeastroapi.com/docs/vedic/dasha) | Confirm period boundary conventions and birth dasha balance against an independent reference. Return the current period first and fetch deep timelines on demand. |
| Ashtakoota Guna Milan | Birth-based matching exposes the eight-factor breakdown and a total out of 36. Manual compatibility is also available. The birth endpoint identifies its ruleset. [Match by birth](https://www.freeastroapi.com/docs/vedic/match) · [Manual compatibility](https://www.freeastroapi.com/docs/vedic/compatibility) | Verify each koota and ordering of both profiles against the tradition Mantrilo intends to support. Display the ruleset and score breakdown, with any flags presented as traditional interpretation. |
| Chart rendering | The Vedic visual endpoint can return raw SVG or PNG in North, South and East Indian layouts. It also supports combined D1 and D9. JSON calculations remain available separately for interactive views. [Visual chart](https://www.freeastroapi.com/docs/vedic/visual-chart) | PNG is the simplest mobile preview. For interactive rendering use normalized JSON, or sanitize SVG before display. Check agreement with the numerical chart, asset size, layout conventions and rights to serve or store images. |
| Daily Panchang | V2 distinguishes sunrise-based daily data from values active at the requested time. It exposes Tithi, Nakshatra, Yoga, Karanas, Rahu Kalam, sunrise and sunset, with ISO timestamps for transitions. It documents an explicit error when sunrise or sunset is unavailable. [Panchang](https://www.freeastroapi.com/docs/vedic/panchang) | Use ISO timestamps for scheduling because display hours can exceed 24. Resolve Rahu Kalam times on the requested local date. Validate transitions and sunrise assumptions. Add sunrise-based Panchang as a separate operation so existing instant results retain their meaning. |
| Accuracy evidence | The vendor publishes an ephemeris benchmark and a versioned schema. [Vendor benchmark](https://www.freeastroapi.com/) · [OpenAPI repository](https://github.com/FreeAstroApi/freeastro-api-spec) | The vendor benchmark does not independently validate the chart, dasha, matching or Panchang rules. Compare equivalent reference frames with [JPL Horizons](https://ssd.jpl.nasa.gov/horizons/) and daily results with [India's Rashtriya Panchang](https://packolkata.imd.gov.in/panchang/en/explanation), accounting for coordinates and sunrise conventions. |
| Mobile payloads and latency | Standalone chart JSON separates planets, houses and metadata. Combined calls save a round trip, but enabling the complete set of modules adds nested timelines and other large objects. [Chart schema](https://www.freeastroapi.com/docs/vedic/chart) · [Combined schema](https://www.freeastroapi.com/docs/vedic/calculate) | Default to the smallest useful response. Measure raw transfer bytes, decoded bytes and end-to-end latency for D1, D1 + D9, daily Panchang and PNG. The docs establish the shape, not performance under Mantrilo traffic. |
| Indian place search and time zones | GeoNames-backed search supports country filtering, state qualifiers and district data where available. Chart requests accept coordinates and an explicit IANA zone, automatic resolution or local mean time. [Geo search](https://www.freeastroapi.com/docs/geo/search) · [Timezone utilities](https://www.freeastroapi.com/docs/utilities/timezones) · [LMT guide](https://www.freeastroapi.com/guide/timezones-and-lmt) | Present duplicate names with state/district, allow a manual pin, and store chosen coordinates, IANA zone, resolved offset and UTC instant. Validate 1940s India, older local mean time, Nepal's 1986 offset and US DST folds/gaps against [IANA tzdb](https://www.iana.org/time-zones). Geo search does not establish historical district coverage. Ambiguous times need an explicit choice. |
| Reliability and rate limits | Vendor docs describe throttling, `429`, `Retry-After` and idempotent retries for billable calculation POSTs. There is a public status dashboard and the vendor publishes a 99.9% uptime target. [Limits and retries](https://www.freeastroapi.com/docs/rate-limits) · [Public status](https://stats.uptimerobot.com/0E0KFhq8CR) | No contractual SLA, historical availability assessment, or guaranteed high-traffic capacity was verified. Treat short rate throttles separately from depleted quota. Retry only when useful with bounded backoff and the same idempotency key for the same request. |

## Commercial terms and launch risks

| Risk | Severity | Decision or evidence needed |
| --- | --- | --- |
| B2B resale and customer reuse | **Launch blocker** | The terms allow paid applications and ongoing storage/reuse of natal and transit calculation output, including after cancellation. They also allow branded interpretations based on those results. They do not expressly confirm that Mantrilo can sell raw or normalized calculations through its own API, sublicense them to customers, or extend that storage right to all Vedic modules and rendered assets. Get written terms for pass-through, downstream caching, redistribution, charts, daily Panchang and matching. Premium report white-labeling on the pricing page is a separate offering. [Terms §7](https://www.freeastroapi.com/terms) · [Pricing](https://www.freeastroapi.com/pricing) |
| Independent calculation accuracy | **Launch blocker** | Compare results using the same UTC instant, Lahiri variant, node type and house convention. Include charts just either side of sign/nakshatra/varga boundaries, historical offsets, day rollover, polar sunrise failures and regional matching conventions. Record unexplained differences before deciding which operations are ready. |
| Birth data and retention | **Launch blocker for personal data** | Send only fields needed for computation. Do not send account identifiers or log birth times or coordinates. The privacy notice permits request-payload logging for up to 30 days and access logs for up to 90 days. Ask for a data processing agreement, deletion terms and reduced retention before sending customer profiles, including both people in a match. [Privacy policy](https://www.freeastroapi.com/privacy) |
| Peak throughput, quota and uptime | **High** | Confirm contracted capacity, incident support and endpoint-level plan entitlements. Queue background calculations, apply a shared upstream rate budget and use a circuit breaker for persistent outages. Never silently switch calculation methods after a vendor error. |
| Vendor rules or schema changes | **High** | Normalize responses at the server, keep provider and ruleset metadata with each calculation, and run saved contract and accuracy cases on provider changes. Include the resolved instant, coordinates, settings and ruleset in cache identity. Keep personal results isolated per workspace. |
| Geodata attribution and ephemeris license | **Medium** | Account for GeoNames attribution when applicable. The published API specification's Apache license applies to the specification. Self-hosting the underlying ephemeris is a separate license decision and is not granted by a hosted API plan. [Terms §7](https://www.freeastroapi.com/terms) · [Specification license](https://github.com/FreeAstroApi/freeastro-api-spec) |

## Pricing and cost per monthly active user

The [published plans](https://www.freeastroapi.com/pricing) show Free at 80 requests/day and 1 request/second, Entry at $8/month for 50,000 requests and 5 requests/second, and High at $40/month for 500,000 requests and 10 requests/second. The Free plan is advertised for public projects. Limits are hard caps. Paid Geo search is advertised as unlimited; confirm whether it shares the per-second budget and whether all V2 features and rendering are included. These estimates assume the listed price and exclude infrastructure, reporting, taxes and any negotiated license.

| Monthly active users | Vendor requests at 4 per active user | Lowest listed paid tier by monthly volume | Vendor cost per active user |
| ---: | ---: | --- | ---: |
| 1,000 | 4,000 | Entry, $8 | $0.0080 |
| 10,000 | 40,000 | Entry, $8 | $0.0008 |
| 50,000 | 200,000 | High, $40 | $0.0008 |
| 100,000 | 400,000 | High, $40 | $0.0004 |
| 100,000 at 8 requests each | 800,000 | Above listed plans | Quote required |

Four calls could be a combined chart, a rendered chart, a match and one additional calculation. Daily widgets change the economics: 10,000 users each making one upstream request per day generate 300,000 calls in a 30-day month. At 50,000 daily users that becomes 1.5 million. With permission to reuse daily calculations, precomputing 20 explicitly labeled city locations once per local date would take about 600 calls per month. Use precise coordinates for personalized results. Peak traffic is a separate constraint: 10,000 requests arriving in a minute need about 167 requests/second; the High plan's 10 requests/second covers about 600 in that minute even if monthly quota remains.

## Implementation path

1. **Start with synthetic requests.** The [probe](../developer/scripts/probe-freeastro.mjs) calls v2 D1, combined D1/D9 with a shallow dasha, and sunrise Panchang. It records status, elapsed time and decoded size and checks required fields. Run it with `FREEASTRO_API_KEY` set in the server environment: `node developer/scripts/probe-freeastro.mjs`. It makes up to three billable or quota-consuming requests and sends no customer data.
2. **Validate independently.** Build fixtures from the sources above. Agree on tolerances before comparing outputs, for example exact labels outside verified boundary cases and a two-minute Panchang transition tolerance where conventions agree. Check DST, local-date rollover, score breakdowns and all three image layouts. Measure percentiles from the Mantrilo service and intended user regions within the purchased request budget. Proposed initial targets are warm p95 under 800 ms for chart or Panchang and under 1.5 seconds for PNG; these are acceptance targets, not observed results.
3. **Add a server-side adapter after the gates pass.** Keep the provider credential out of Expo, issue separate normalized operations for chart, daily Panchang and matching, and preserve the current API's response contract. Cache only the outputs and durations allowed by agreement. Precompute shared daily results and use the vendor idempotency contract for retries. Measure upstream errors, queue delay and quota usage without logging personal inputs.
4. **Reassess if resale or peak capacity is denied.** Seek a provider with explicit API redistribution rights and a capacity commitment, or evaluate a separately licensed, independently validated self-hosted engine.
